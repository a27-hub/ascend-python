## 定界与根因

### 现象
- `-e 50` 快检：50 例全部执行 SUCCESS（无 FAILED），但精度仅 29/50 通过，**21 例精度不通过**。
- 21 例精度不通过与 `dstType=29`(int4) **完全相关**；所有精度通过例均为 `dstType=2`(int8)。

### 根因链（executor 适配层 · int4 输出表示）
NPU 算子 `aclnnSwiGluQuantV2` 对 int4(dst_type=29) 输出返回 **uint8 打包格式**：每个 uint8 字节按 `(低4位, 高4位)` 承载两个有符号 int4；整张 golden 的 int4 值（shape 末维 = x末维/2）按行优先展平后打包进 uint8 序列前段，尾部 padding=0。
而 CPU golden 返回 **有符号 int8**，每元素一个 int4 值。

executor 初始移交件里对 int4 的处理有两处错误：
1. 第一版（我按“kernel 未打包”假设去掉解包）→ npu y 末维 = golden 2 倍 → `the size of npu output[N] and benchmark[N/2] is not equal`。
2. 若沿用原死代码 `pta_tensor_int8_to_int4s`（末维直接 ×2，无 padding 裁剪）→ 元素数错 / 值域错（uint8 直接当值，出现 178/255 等越界值，`max_diff≈256`=有符号↔无符号偏移）。

**正确解包**（已实测 case13 与 golden 逐值一致，MATCH=True）：
npu uint8 flatten → 交错拆低/高 nibble → 各自 nibble 符号扩展（≥8 → −16）→ 取前 `prod(golden_shape)` 个 → reshape 成 golden 形状（末维 = x末维/2）。

### 修复
仅改 **ATK executor 适配脚本**（`executor_swiglu_quant.py` 的 NPU 分支 + 新增 `npu_int4_unpack_to_golden`），**未改动 op-plugin 算子 C++ 代码**。因此不进 flow-fix / op-adaptation(MODIFY)。
